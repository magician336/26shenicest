# 0002: 小游戏采用"信息不对称 + 无失败"的非对称合作设计

## Status

accepted

## 决策

小游戏阶段为**非对称合作**：双方各自操作各自不同的场景（信息不对称），靠现实语音沟通交换信息过关。**小游戏没有失败结局、没有倒计时**；一方卡住时另一方只能等待。角色差异仅限外观/身份，不影响玩法。

## 背景

联机需求确认后，"双人同屏探索"假设被推翻：探索阶段固定一人（Host）操作上屏角色，另一人（Client）观战；小游戏阶段才双方登场。用户明确要求"两个人有不同的场景，需要沟通才能过关"，且"只有胜利，没有失败，如果一方卡住，只能等待"。

## Considered Options

- **失败态 + 倒计时（传统小游戏）**：现有 `MiniGameSettings` 带 10s 时限与失败判定。落选：与"无失败、卡住等待"的产品取向冲突；倒计时对信息不对称的沟通游戏构成不公平压力（信息掌握快的一方惩罚慢的一方）。
- **超时重置本轮**：保留压力但"重置进度"是软惩罚，同样与取向冲突。
- **倒计时仅作记录**：保留节奏但无惩罚；用户仍选择彻底去掉，尊重其取向。

## Consequences

- **`MiniGameSettings.timeLimit` 不再使用**（可移除或忽略）；`MiniGameBase` 的 `IsSuccess` 语义简化为"是否已完成"，`IsComplete` 即成功。
- **触发权唯一**：只有探索操作者（Host）能触发小游戏，Client 无触发入口。
- **实现**：小游戏逻辑由 Host 权威模拟，`[Networked]` 状态同步；各客户端 UI 层只渲染自己角色对应的场景；点击/拖拽等本地交互通过 RPC 上报 Host 判定。
- **风险**：若设计"只有成功"，玩家可能无限卡关。接受此风险——等待是游戏机制的一部分；若后续要加引导/提示，作为独立小功能添加即可，不改架构。
